# なんちゃってECサイト 基本設計 初期案

# ■ 設計方針

Phase1では、以下を優先する。

- ECサイトとして最低限成立する導線を作る
- 商品・カート・注文・レビューのドメインを分ける
- 軽量DDDを試すが、過剰抽象化は避ける
- TDD対象は業務ルールがある箇所に絞る
- 管理者機能はPhase1後半またはPhase2寄りにする

---

## 3. Category

商品カテゴリを扱う。

### 主な属性

- id
- name
- slug

---

## 4. Cart

ユーザーごとの購入予定商品を扱う。

### 主な属性

- user_id
- cart_items

### CartItem

- product_id
- quantity
- unit_price_snapshot

### 業務ルール

- 数量は1以上
- 在庫数を超えて追加不可
- 販売停止商品は追加不可
- 合計金額を計算できる

---

## 5. Order

疑似注文を扱う。

### 主な属性

- id
- user_id
- status
  - ordered
  - canceled
- total_amount
- ordered_at

### OrderItem

- order_id
- product_id
- product_name_snapshot
- unit_price_snapshot
- quantity
- subtotal

### 業務ルール

- 注文確定時に在庫チェック
- 注文確定時に商品情報・価格をスナップショット保存
- 注文確定後にカートを空にする
- 在庫を減算する

---

## 6. Review

商品レビューを扱う。

### 主な属性

- id
- product_id
- user_id
- rating
- comment
- created_at
- updated_at

### 業務ルール

- rating は 1〜5
- 1ユーザー1商品1レビューまで
- 購入済みユーザーのみ投稿可能
- status は draft / published / hidden
- 商品詳細で平均評価を表示する

# ■ 基本設計上の検討事項

## 1. カートをDB管理にするか

Phase1ではDB管理が良い。

### 理由

- ログインユーザー単位で扱える
- 注文確定と連携しやすい
- ECドメインの学習になる

---

## 2. 商品価格を注文時にスナップショットするか

するべき。

### 理由

- 注文後に商品価格が変わっても注文履歴が壊れない
- 実務寄りEC設計として自然

---

## 3. 在庫をいつ減らすか

Phase1では注文確定時に減らす。

予約在庫や仮押さえはPhase1では扱わない。

---

## 4. レビュー投稿制限

Phase1では以下のどちらか。

### 案A

- 1ユーザー1商品1レビューまで

### 案B

- 制限なし

### おすすめ

案A。

### 理由

- 平均評価が自然
- ユニーク制約で守りやすい
- 後から購入者限定レビューへ拡張しやすい

---

## 5. 管理者機能の優先度

Phase1に含めてもよいが、実装順は後半が良い。

先に商品seedで商品閲覧・カート・注文を作る方が安全。
